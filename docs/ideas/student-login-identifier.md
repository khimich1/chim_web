# Логин ученика (вместо email в UI)

## Problem Statement

Как дать учителю заводить ученика по удобному логину (латиница), чтобы школьник без почты мог войти, не меняя модель аккаунта и не усложняя восстановление доступа?

## Recommended Direction

**Направление A:** одно поле **«Логин»** с хранением в существующей колонке `users.email` (уникальная строка).

Учитель вводит логин латиницей (`masha`, `ivanov2026` или привычный `masha@school.ru`). Ученик входит тем же значением + временным паролем. Восстановление доступа — только через преподавателя (сброс пароля).

**UI и тексты:** везде «логин», не «email» — форма создания, экран входа, списки, карточка ученика, ошибки, подтверждения (сброс пароля / удаление), уведомления где показывается идентификатор ученика.

**Формат логина:** только латиница (и допустимые символы идентификатора). Кириллица запрещена.

Правило MVP:

- длина 3–64 (или до текущего лимита колонки, но UX-разумный верх)
- символы: `a-z`, `A-Z`, `0-9`, `._@+-` (`@` разрешён — email-подобные логины ок)
- без пробелов и кириллицы
- **нормализация:** `lower()` при сохранении и при поиске на входе (`Masha` ≡ `masha`)
- unique, как сейчас

На фронте: убрать `type="email"`, label/placeholder/ошибки → «Логин». На бэке: валидация формата + `lower()` при создании ученика и при authenticate; поле API может остаться `email` в JSON на MVP — в OpenAPI/описании пометить как identifier/login.

Отдельную колонку `login` / `username` **не вводим**, пока нет продукта вокруг настоящей почты.

## Key Assumptions to Validate

- [ ] Учителям достаточно логина в списках без отдельного «Имя / ФИО»
- [ ] Имя поля API `email` при UI «Логин» приемлемо на MVP (техдолг на rename позже)
- [ ] Существующие ученики с email-логинами продолжают входить после `lower()` (данные уже в lower или миграция one-shot)
- [ ] Учителя входят тем же полем «Логин» (их идентификаторы уже латиница/email)

## MVP Scope

**В scope:**

- Форма «Новый ученик»: поле «Логин», без HTML `type="email"`, клиентская подсказка про латиницу
- Экран входа: «Логин» + тексты ошибок («Неверный логин или пароль»)
- Списки / карточка / диалоги: показывать и называть идентификатор как логин
- Backend: валидация латиницы + `@`/допустимые символы, `lower()` при create и login, сообщение коллизии про логин; пароль мин. **4**
- Тесты: create с логином без `@` и с `@`; reject кириллицы; login case-insensitive; пароль 4 ок / 3 → 422; обновлённые UI-тексты
- `seed_teacher`: тот же минимум пароля 4

**Вне scope:**

- Миграция БД / rename колонки `email` → `login`
- Self-service восстановление пароля
- Display name / ФИО
- Автогенерация логинов, invite-коды, SSO
- Отдельная колонка username

## Not Doing (and Why)

- Отдельная колонка `login` — лишняя сложность при той же UX-ценности сейчас
- Кириллица в логине — путаница раскладок, коллизии визуально похожих символов
- Обязательный «настоящий» email — противоречит боли «нет почты»; recovery через учителя
- Синтетический суффикс (`ivan@local`) — скрытая магия
- Полный rename API/БД `email` → `login` в том же MVP — раздувает diff без выигрыша для учителя

## Open Questions

- Верхняя длина: 64 vs текущие 320 в схеме?
- Нужен ли hint под полем: «Только латиница, например `ivanov`»?
- Нужен ли one-shot `UPDATE users SET email = lower(email)` для уже существующих аккаунтов?

## Decisions (зафиксировано)

| Решение | Выбор |
|--------|--------|
| Направление | A — reuse `users.email` |
| Бенефициар | Учитель (удобство онбординга) |
| Recovery | Только через преподавателя |
| UI-терминология | Везде «логин» |
| Алфавит логина | Только латиница (кириллица нет) |
| Символ `@` | Разрешён (email-подобные логины) |
| Нормализация | `lower()` при сохранении и поиске |
| Мин. пароль | **4** символа (ученик create + `seed_teacher`) |
